# Verifiable Authorization for Autonomous Agents
## A Cryptographic Execution Boundary for the Agentic Enterprise

**VeriLinkOS Architectural Briefing | August 2026 | Version 5.0**

---

## 1. Executive Summary
The emergence of autonomous AI agents has shifted cybersecurity from protecting static perimeters to governing dynamic, machine-scale actions. While agentic systems offer unprecedented capability, they introduce a fundamental security vulnerability: the gap between AI-generated intent and actual execution. This document outlines the core architectural proposition of the **Verifiable Action Protocol (VAP)**: **The Intent–Execution Separation Principle.** VAP turns authorization from an implicit decision into an explicit, portable, and cryptographically verifiable artifact that binds bounded authority to the exact action being executed.

---

## 2. The Intent–Execution Separation Principle
The central proposition of VAP is the **Intent–Execution Separation Principle**:

> **Agent-generated intent and authorized execution must be cryptographically separable.**

In a VAP-enabled architecture, an agent may propose an action, but the execution boundary is solely responsible for determining if that action is authorized, within policy, and cryptographically sound. **A compromised agent should be capable of generating malicious intent without possessing the authority required to execute it.**

---

## 3. Why Conventional Authorization is Insufficient
Conventional authorization (`Identity → Role → Permission`) is centered on whether a principal is permitted to invoke an operation. Agentic systems introduce a new requirement: **consequential actions must carry bounded, verifiable authority through the execution path.**

| Feature | Conventional IAM | VeriLinkOS (VAP) |
| :--- | :--- | :--- |
| **Authorization Unit** | Principal / resource / operation | Bounded action (Contextual) |
| **Authority** | Permission (Static/Dynamic) | Signed Authorization Artifact |
| **Enforcement** | Policy decision (PDP/PEP) | Action-level verification (Match) |
| **Provenance** | Platform records (Logs) | Cryptographically bound evidence |
| **Verification** | Platform-dependent | Independent / Cross-Domain |

Conventional IAM establishes *general* access, but fails to constrain *individual* consequential actions. VAP establishes authority *bound to the action itself*.

## 4. The VAP Primitive: What is a PERMIT?
A PERMIT is not an instruction to execute; it is a **signed statement of bounded authority** that an execution boundary can independently verify against a proposed action.

### Anatomy of a PERMIT Artifact
* **Identity:** Principal and Agent Identity.
* **Authorization Scope:** Operation type, target scope, policy binding (id/version/hash).
* **Constraints:** Machine-enforceable limits (e.g., `amount <= 200 EUR`, `recipient_hash = X`).
* **Validity:** Temporal expiration and replay protection (nonce).
* **Cryptographic Commitment:** Signature by the Governance Authority.

### The "MAY-DID-MATCH" Model
VAP implements a three-part conceptual framework for autonomous authority:

*   **PERMIT (MAY):** The Authority attests that the Agent *may* perform a class of actions within signed constraints.
*   **REQUEST (DID):** The agent attempts to perform a specific action, presented with the PERMIT artifact.
*   **ENFORCEMENT (MATCH):** The execution gateway cryptographically verifies that the *DID* satisfies the *MAY* constraints. 

**Execution is denied if a mismatch is detected.**

## 5. End-to-End Example: Autonomous Procurement Agent

**Authorized State**
Agent is authorized for payments up to €200 to `Vendor X` under `Policy v2.1`.

**Attack Scenario**
Agent is compromised by prompt injection and proposes: `Buy €4,000 from Vendor Y`.

**Enforcement (The MATCH Boundary)**
The gateway evaluates the proposal against the PERMIT:
*   **Signature Valid:** ✓
*   **Policy Binding (Hash Match):** ✓
*   **Constraint Verification (Amount ≤ €200):** ✗
*   **Constraint Verification (Recipient Match):** ✗

**Result:** **🚫 EXECUTION DENIED (No settlement generated).**

*The agent was compromised, but its execution authority was not.*

## 6. Threat Model & Defensive Invariants
VAP enforces security invariants at the execution boundary rather than relying on perimeter defenses.

| Attack Vector | Defensive Invariant | Protection Strategy |
| :--- | :--- | :--- |
| **Prompt Injection** | **Constraint Enforcement** | Gateway rejects actions violating PERMIT limits. |
| **Privilege Escalation** | **Action-Bound Authority** | Agents possess authority for *this* action, not *all* actions. |
| **Policy Substitution** | **Policy Hash Binding** | Execution rejected if policy binding is tampered with. |
| **Replay Attack** | **Nonce Tracking** | Gateway rejects previously consumed permit identifiers. |
| **Log Alteration** | **Immutable Receipts** | Evidence is independently verifiable; platform logs are secondary. |

*Note: Cryptography does not magically enforce security; the execution gateway must independently verify these constraints in real-time.*
